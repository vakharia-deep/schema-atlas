# Local service boundaries

Schema Atlas is a read-only catalog viewer and SQL workspace for the operating-system user running it. It binds to `127.0.0.1` and is accessed from another machine through an authenticated SSH tunnel. It is not an Internet-facing multi-user service. Processes acting as the same OS user are not isolated from it.

## Database access and credentials

- Catalog inspection runs only fixed SQL. Object OID arrays are bound parameters. Startup sets `default_transaction_read_only=on`; every scan explicitly begins a `REPEATABLE READ READ ONLY` transaction and sets a local `pg_catalog` search path. The transaction's read-only state is checked. Catalog scans never read table rows. The separate SQL workspace can read rows with the connected role’s permissions.
- Use a dedicated non-superuser database role with only the required SELECT/EXECUTE grants. READ ONLY is a PostgreSQL transaction policy, not a sandbox for functions or extensions with external side effects. The database administrator controls those privileges. The integration fixture verifies catalog access without table SELECT grants. Server/network and managed-service catalog policies remain external controls.
- Remote database connections require TLS with `rejectUnauthorized: true`, TLS 1.2 minimum, and certificate identity checked against the original host. Optional custom CA certificates are scoped to that connection. Cleartext mode is accepted only for loopback destinations, allowing local PostgreSQL and an existing SSH tunnel.
- Hosts are validated as IP addresses or DNS names. The entire DNS answer set is checked, then the selected validated address is pinned for the connection. Unspecified, multicast, link-local/metadata-service and mapped equivalents are rejected. Private database networks are intentionally supported. This is a PostgreSQL client capability, not a general HTTP proxy.
- Temporary connections retain validated credentials only in memory. Saved profiles persist them as authenticated AES-256-GCM ciphertext; the encryption key is held in the OS credential store, never in the profile file. Public inventories and exports omit passwords and CA configuration. Passwords never enter localStorage. Password fields reset after success/cancellation. Disconnect, expiry and shutdown clear active provider references. JavaScript garbage collection does not guarantee memory zeroization.
- Each scan opens one PostgreSQL client and closes it in `finally`. There is no idle pool. DNS resolution has a five-second deadline, connection establishment six seconds, statements eight seconds, locks two seconds, idle transactions ten seconds, and scans 25 seconds.

## Browser and HTTP boundaries

- Host allowlisting, same-Origin checks and cross-site fetch rejection protect the loopback service. CORS is not enabled. Every mutation requires a browser-specific random 256-bit CSRF token and a matching random session cookie. Connections are looked up only in the owning session; possessing another connection ID is insufficient.
- Session cookies use `HttpOnly`, `SameSite=Strict`, `Path=/` and an eight-hour maximum age. They lack `Secure` only because this service uses loopback HTTP; SSH protects the cross-machine hop. There is a 30-minute idle and eight-hour absolute server session lifetime. Cleanup runs on requests and every minute. Browser close alone does not guarantee immediate credential removal; use Disconnect.
- Fixed static routes expose only the web assets. Connection and query JSON accept only their respective allowed fields. Both validate types and length, reject unknown keys, and cap input at 48 KB. Refresh/disconnect/cancel/profile-action endpoints reject request bodies. Generic connection errors omit driver messages, SQL, passwords and stack traces.
- Budgets: 300 HTTP requests/minute, 30 refreshes/minute, ten connection attempts/minute/session, two concurrent scans, four active connections/session, 20 sessions and 40 HTTP connections. Request/header timeouts are configured. These are single-process controls.
- Catalog scans enforce row caps (2,000 tables, 50,000 columns, 20,000 indexes/constraints/inheritance edges, 10,000 triggers/policies and 30,000 ACL entries), a 16 MB aggregate result budget, and display-length limits for definitions/comments. A limit error retains the prior snapshot. The graph is intended for bounded schemas, not unrestricted database sizes.
- All metadata, SQL history and result cells are rendered through text nodes and fixed DOM attributes. No database string is inserted as executable HTML. There are no third-party scripts, fonts, CDNs or telemetry. CSP denies inline scripts and framing; inline styles support graph positions. Responses also carry no-store, no-referrer, MIME protection and restricted permissions headers.
- Schema exports contain database metadata such as definitions, comments, hostnames and roles; handle them accordingly. The browser can optionally persist diagram coordinates, but not connection credentials.

## Saved profile storage

- A random 256-bit `atlas_browser` capability cookie identifies the saved-profile owner across process restarts. It is HttpOnly, SameSite=Strict, host-only, path `/`, with a rolling one-year lifetime. HTTP is only for loopback; remote access must use an authenticated SSH tunnel. Clearing/private-session expiry loses this identity; cross-browser recovery is not implemented.
- The server derives an owner digest from that token. Every saved-profile list, lookup, reconnect, save and removal is scoped to this owner before credentials leave storage. No API accepts an owner field. Active session cookies and CSRF tokens remain separate and required for mutations. Browser identity mismatches invalidate the active session. Possession of a profile ID alone does not grant access; executable tests exercise a second browser.
- Complete profile documents are encrypted using Node's AES-256-GCM, fresh random 96-bit nonces, 128-bit tags and owner/version authenticated associated data. Swapping ciphertext between owners, tampering, wrong/missing keys and invalid schemas fail closed without overwriting files. Stored connection fields are revalidated before use; DNS, TLS and destination validation still applies on reconnect.
- The random 256-bit key is accessed through pinned `@napi-rs/keyring`; Linux explicitly requires persistent Secret Service rather than a volatile fallback. Key access has an eight-second abort signal. No plaintext/local-file-key fallback exists. A live native-store round trip was verified on macOS; Windows/Linux remain unverified. Loss of the key requires removing the inaccessible vaults and saving database credentials again. Key rotation/recovery UI is not included.
- Vault files live outside the source tree, bounded to 1 MiB per owner, with at most 20 profiles per owner and 128 owner files. Owner-derived filenames are strictly validated. Reads reject symlinks and non-regular/oversized/over-permissive files. Directories/files use 0700/0600 on POSIX. Writes use private exclusive temporary files plus atomic rename and are serialized within the process. Run one server per storage directory; this is not a distributed store. The OS account and its unlocked credential store are trusted.
- Disconnect removes active credentials but preserves the profile. Forget removes saved credentials without changing database contents or closing active queries; backups may retain older ciphertext. If storage fails, Disconnect still closes active credentials and reports that its auto-reconnect selection could not be cleared. Losing the browser cookie leaves an inaccessible encrypted file on the server; forget profiles before clearing cookies.

## SQL execution

- Run and cancel routes require the session cookie, CSRF token, connection ownership and the query ID linked to that connection. SQL cannot supply a separate host or credentials. The same validated/pinned transport and verified TLS settings are reused.
- SQL is the explicit purpose of the editor, not an interpolated application parameter. The statement is sent unchanged using pg's extended protocol (one statement). A leading-command allowlist admits SELECT/WITH/EXPLAIN/SHOW/TABLE/VALUES; PostgreSQL READ ONLY enforces the actual write policy, including data-modifying CTEs and EXPLAIN ANALYZE. Every run has a new connection and is rolled back, then closed.
- Limits: 32 KB SQL, 1,000 rows, 200 columns, 2 MB retained JSON, 8 MB protocol bytes counted before pg parses them, 100–20,000 ms server statement timeout, and an external deadline six seconds longer. Excess rows return a visibly truncated result; oversized individual protocol values fail. Raw text parsers preserve exact numbers and avoid recursive JSON/array parsing. No total row count is inferred from a truncated result.
- Cancellation pauses the result socket, sends parameterized pg_cancel_backend through a separate authenticated connection to the same pinned target (3.5-second maximum), then destroys/closes the query client. Connection teardown and the statement timeout are fallbacks if cancellation cannot reach PostgreSQL.
- One query per browser session, two globally, 30 attempts/minute/session and 60/minute/server. Client disconnect, saved-connection disconnect, expiry and shutdown stop active jobs.
- Driver error text, detail, notices and SQL are never echoed or logged. A fixed error category, validated SQLSTATE and bounded numeric error position help the editor without exposing row values or function internals.
- History stores at most 20 statements per connection in tab memory. Results remain only in browser memory unless explicitly exported. No SQL/result localStorage or server result cache exists. PostgreSQL's own logging is controlled by the database administrator.

## Query profiling

- Profiling uses the same session/CSRF/connection ownership, transport, single-statement read-only execution and cancellation boundaries as the SQL workspace. It shares the SQL concurrency and request budgets. Parameters are bound values, limited to 64 scalars and 16 KB total. No connection, owner or file path is accepted in a profiling request.
- Statistics queries use fixed SQL and bound role scope. The extension schema is obtained from the catalog and quoted as an identifier. Statistics are restricted to the selected database; non-privileged roles see their own entries. Tool-generated statistics queries are marked and excluded.
- Application plans come only from `pg_current_logfile('jsonlog')` on the selected server. Caller-supplied file paths are unsupported. The connected role must already have PostgreSQL permission to read this log. Before returning plans, records are restricted by database and role scope, unrelated records are discarded, and the plan is reconstructed into bounded display fields. Raw logs and server paths never reach the browser.
- Captures retain bounded statistics and an internal log cursor in the owning server session for at most 30 minutes of usable capture time. Disconnect/expiry/shutdown releases them. Log reads stop at 512 KB and 2,500 records; plan output stops at 100 plans, each at most 1,000 nodes and 40 levels. Rotation, truncation and counter resets are reported as incomplete evidence.
- Profiling does not install extensions, change server settings, create indexes or reset counters. Setup is diagnostic. Database-managed logging continues independently of browser capture; SQL literals can be present in PostgreSQL logs. The suggested auto_explain configuration disables parameter logging. Results/baselines remain in browser memory, with eight retained plans per connection.
- Index usage reads fixed PostgreSQL catalog/statistics queries in the selected connection, restricted to schemas with USAGE. It uses the existing ownership, CSRF, read-only, cancellation and rate/concurrency limits. Snapshots cap both indexes and tables at 1,000 and report incomplete coverage. Counters establish aggregate activity only; disabled track_counts is reported.
- Slow-query files are never uploaded or stored server-side. Extension/MIME and size checks run before a disposable browser worker receives the file. The worker validates the byte limit again, decodes UTF-8 strictly, restricts JSON depth to 16, and projects only known scalar display fields. Input is capped at 2 MB / 20,000 lines, output at 500 records / 1 MB, and SQL at 30,000 bytes per record; the parent terminates the worker after three seconds. These limits bound this text parser; browser memory/process isolation is provided by the browser, not a server sandbox. No filesystem paths, decompression, dynamic evaluation or raw-HTML rendering are involved.
- Structured imported records are filtered by the selected database; unscoped stderr records show an explicit database warning. Bind details are not imported. Opening SQL in the editor does not execute it; explicit EXPLAIN requests still pass the server query validation and read-only gate. Imported records stay in per-connection browser memory and clear on request, reload or disconnect.

## Verification

Tests cover cross-origin/host/CSRF rejection; browser session ownership and expiry; input/egress validation; connection caps; password removal; least-privilege real PostgreSQL catalog access; consistent read-only scans; TLS trust and hostname verification; refresh additions/removals; failure retention; query RLS/permissions, bounded output, exact values, cancellation/timeout cleanup and single-statement/read-only enforcement. Dependencies are pinned in `package-lock.json` and checked with `npm audit --omit=dev`. Snyk is not installed on this host, so a SAST result is unavailable.
